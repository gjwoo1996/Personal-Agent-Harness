# Dev Container Standards

This is the authoritative dev container rule document distributed by Personal-Agent-Harness.
AI agents should read this English document as the rule source for dev-container-related work.

## Status

This document is the final consensus distilled from earlier Claude, Composer, and Codex dev container notes in the original workspace. Those notes were inputs; this document is the standard.

Priority order:

1. Direct user instruction
2. Project-specific dev container rules and documented exceptions
3. This document
4. Historical notes or translations

Korean translations are for human reading only. Do not use `*.ko.md` files as AI rule sources.

## Final Consensus

Use Composer's practical developer experience as the default structure, Codex's reproducibility and verification rules as the completion bar, and Claude's maintainability and onboarding rules to control exceptions.

In practice:

- Start from Docker Compose, even when the first version has only a `workspace` service.
- Use `vscode` and `/home/vscode/${localWorkspaceFolderBasename}` as the default identity and workspace path.
- Install language runtimes with devcontainer features first.
- Use official devcontainer Features for AI CLIs when available; otherwise install pinned CLIs in the Dockerfile.
- Decide AI state storage with the decision tree below instead of using one universal mount strategy.
- Keep long-lived rules in this document, not duplicated across AI-specific entry files.

## Standard File Layout

Use this layout for new dev containers:

```text
.devcontainer/
├── devcontainer.json
├── docker-compose.dev.yml
├── Dockerfile
├── commands/
│   ├── initializeCommand.sh
│   ├── post-create.sh
│   └── post-start.sh
├── .env
├── .env.example
└── README.md

.env
.env.example
```

Rules:

- Use `.devcontainer/commands/` for lifecycle scripts.
- Do not mix `scripts/` and `commands/`.
- Prefer `docker-compose.dev.yml` for dev-only Compose configuration.
- Keep `.devcontainer/.env` for Compose interpolation values generated by `initializeCommand`.
- Keep root `.env` for app/runtime values and root `.env.example` for non-secret examples.

## Compose-First Rule

Every new project should start from Compose:

- `devcontainer.json` should point to `docker-compose.dev.yml`.
- The primary service should be named `workspace`.
- Databases, caches, search engines, and similar sidecars should live in the same project Compose file.
- Service-to-service communication should use Compose service names, such as `postgres:5432`.

Do not make new projects depend on shared external stacks such as `Common_Repo` or a shared Docker network by default. Such dependencies are legacy or exceptional patterns and must be documented in `.devcontainer/README.md`.

## User And Workspace Path

Default:

```json
{
  "remoteUser": "vscode",
  "updateRemoteUserUID": true,
  "workspaceFolder": "/home/vscode/${localWorkspaceFolderBasename}"
}
```

Rules:

- Do not hardcode `/workspace/<project-name>` or `/workspaces/<project-name>`.
- Do not default to `node` just because the project uses Node.js.
- Use `node` only when a selected base image is explicitly designed around the `node` user, and document the exception.
- If the remote user changes, update home paths, mounts, and lifecycle scripts consistently.

## Runtime And Tool Installation

Use this responsibility split:

- Language runtimes and common development stacks: devcontainer features.
- AI CLIs and tools unavailable or unsuitable as features: Dockerfile.
- Project dependencies: lifecycle command, usually `post-create.sh`.

Default Dockerfile base:

```dockerfile
FROM mcr.microsoft.com/devcontainers/base:ubuntu
```

Use a heavier stack image or custom Dockerfile logic only when:

- A required tool cannot be installed cleanly through features.
- The project needs a stack-specific Microsoft devcontainer image.
- The Dockerfile already needs several custom apt/system dependencies.
- A pinned, audited installation path is required.

## Version Pinning

Do not use `latest` or floating `lts` values in the standard template.

Pin:

- Base images
- Devcontainer feature versions
- Language runtimes
- Database and sidecar images
- `CODEX_CLI_VERSION`

Version updates should be intentional changes with a rebuild and smoke-test result.

Claude Code defaults to the official Feature's update channel. If a project chooses
an npm-pinned Claude Code install instead, it must disable Claude's autoupdater and
document why the exception is needed.

## AI CLI Installation

Install AI CLIs during image build or through devcontainer Features, not in `postCreateCommand`.

Rules:

- Use the official Claude Code devcontainer Feature by default.
- Install Codex CLI in the Dockerfile with `CODEX_CLI_VERSION` by default.
- Use Dockerfile build args for AI CLI versions installed in the Dockerfile.
- Pin those Dockerfile-installed versions to validated values.
- Print or verify CLI versions during build or `post-create.sh`.
- Do not install the same AI CLI through both a devcontainer feature and the Dockerfile.

Example intent:

```dockerfile
ARG CODEX_CLI_VERSION
RUN npm install -g \
    "@openai/codex@${CODEX_CLI_VERSION}" \
    && codex --version
```

```json
"features": {
  "ghcr.io/anthropics/devcontainer-features/claude-code:1.0": {}
}
```

## AI State Storage Decision Tree

There is no single universal default. Choose based on the project context.

Use host bind mounts when:

- This is a personal WSL2 development environment.
- The same human uses host Cursor, host CLI, and devcontainer CLI interchangeably.
- Reusing existing host login/session state is more important than project isolation.
- The host path and required setup are documented.

Use named volumes when:

- The project is a team template.
- The project needs project-specific AI accounts or API isolation.
- CI, onboarding, or new-machine reproducibility matters more than host convenience.
- The container environment should work without pre-existing host AI state.

Always:

- Use stable volume names such as `{project-slug}-claude-config` and `{project-slug}-codex-config`.
- Never include `${devcontainerId}` in AI state volume names.
- Preserve both directory state and file state, including Claude's `.claude.json` when needed.
- Document the selected strategy in `.devcontainer/README.md`.

Read-only host binds are acceptable for external credentials such as OCI or SSH files when the project genuinely needs them. Document the path, purpose, and expected permissions.

## Secrets And Environment Variables

Separate secrets and configuration by responsibility:

- Personal/API secrets: `containerEnv` with `${localEnv:...}`.
- App and database runtime values: root `.env` and `.env.example`.
- Compose interpolation values: `.devcontainer/.env`, generated by `initializeCommand.sh`.
- Non-secret examples only: `.env.example`.

Rules:

- Do not commit real secrets.
- Do not put real API keys in `.env.example`.
- Do not bake secrets into Docker images.
- Do not require a developer to copy private values into a committed file.

## Lifecycle Commands

Use `.devcontainer/commands/` only.

`initializeCommand.sh`:

- Runs on the host.
- Creates `.devcontainer/.env` for Compose interpolation.
- Should be fast and idempotent.

`post-create.sh`:

- Runs once after container creation.
- Should use `set -euo pipefail`.
- Installs project dependencies.
- Verifies runtime and AI CLI versions.
- Configures `git safe.directory` when required.
- Must be idempotent.

`post-start.sh`:

- Optional.
- Keep it lightweight.
- Use it only for quick permission checks or health hints.
- May run lightweight, idempotent AI skill repair when AI state is backed by named volumes.

Do not run destructive or state-changing app operations automatically:

- No database migrations by default.
- No seed data by default.
- No long-running app servers by default.
- No hidden best-effort failure swallowing.

## AI Skill Setup (superpowers / gstack)

Distributed templates should document AI skill setup, but should not automatically
install skills unless the target project explicitly opts in.

When a project opts in, use these principles:

- Store AI state in named volumes when the setup should survive rebuilds without host paths.
- Repair skills idempotently in `post-start.sh` so missing symlinks or plugin state recover.
- Support optional repository ref pins for skill repositories.
- Degrade gracefully for missing CLIs, temporary marketplace failures, and browser health failures.
- Fail fast for broken shell syntax, missing local script files, and permission repair failures.

The maintainer implementation at `.devcontainer/commands/ensure-ai-skills.sh` is the
reference pattern for superpowers and gstack/browse setup.

## Ports And VS Code Extensions

Expose only what a developer needs from the host.

Rules:

- App ports may be listed in `forwardPorts`.
- Pair each forwarded port with `portsAttributes`.
- Use `openBrowser` for the main web UI when appropriate.
- Keep database/cache/search ports internal unless a host GUI workflow requires exposure.
- Document host-published sidecar ports as exceptions.

Keep shared VS Code extensions minimal:

- Required AI extensions only by default.
- Stack-specific extensions, such as ESLint or Prettier, are allowed only when the project stack needs them.
- Personal preference extensions, themes, and icon packs should not be required by the shared devcontainer.

## Exception Documentation

Whenever the project deviates from this standard, create or update `.devcontainer/README.md`.

Document:

- What differs from the standard
- Why the exception is necessary
- Security and reproducibility impact
- Required host setup
- Commands to verify the environment
- How to migrate back to the standard if applicable

Exceptions that must be documented include:

- Host bind mounts for AI state
- Shared external Compose stacks or Docker networks
- Published sidecar ports
- Non-`vscode` remote users
- Harder Dockerfile-based runtime installation
- Read-only external credential binds

## Verification Checklist

A devcontainer change is not complete until these checks are considered and the relevant ones pass:

- `docker compose -f .devcontainer/docker-compose.dev.yml config`
- First "Reopen in Container" succeeds.
- Rebuild succeeds.
- `whoami` returns the expected remote user.
- `pwd` matches `/home/vscode/${localWorkspaceFolderBasename}` unless a documented exception exists.
- Runtime versions match the pinned configuration.
- `claude --version` succeeds when Claude Code is included.
- `codex --version` succeeds when Codex CLI is included.
- AI state remains available after rebuild according to the selected storage strategy.
- App dependency installation succeeds.
- Main app port smoke test succeeds when the project has a web app.
- No real secret values appear in committed files.
