# 01. 요청 배경

> **과거 기록(2026-06-09):** 이 문서는 당시 문제 정의를 보존합니다. 현재 사용법은 [06-사용법-요약.md](06-사용법-요약.md)를 따릅니다.

## 최초 요청 (2026-06-09)

Personal-Agent-Harness를 **다른 프로젝트에 적용**할 때, 기존 문서/README에 안내된 방식은 다음과 같았다.

```bash
# 대상 프로젝트 루트에서
git clone <repo-url> Personal-Agent-Harness && ./Personal-Agent-Harness/setup.sh
```

### 발생한 문제

1. **중첩 git 저장소**
   - 대상 프로젝트: `my-project/.git`
   - 하네스 clone: `my-project/Personal-Agent-Harness/.git`
   - 두 개의 독립 git이 한 트리 안에 존재

2. **불필요한 폴더**
   - copy mode인데도 harness **전체 소스**(`standards/`, `bin/`, `docs/` 등)가 프로젝트 안에 남음
   - 실제로 필요한 것은 복사된 `docs/`, `.cursor/rules/`, `.harness/manifest.json` 뿐

3. **운영 혼란**
   - harness 폴더를 git에 커밋할지 말지 불명확
   - `git status` / IDE git 뷰 혼란
   - 팀원마다 harness 버전이 달라질 수 있음

### 사용자 목표

- superpowers brainstorming 스킬을 활용해 **해결 방안 논의**
- 중첩 git 없이 harness를 쓰는 **권장 워크플로우** 확립
- (이후) 업계에서 많이 쓰는 **npm/npx CLI + 프로젝트에 파일 복사** 패턴으로 전환

## copy mode와의 관계

하네스는 원래부터 **copy mode**다.

- harness 저장소 = 원본
- 대상 프로젝트 = 규칙 파일 복사본 + manifest

문제는 copy mode 설계와 **배포/설치 UX**(프로젝트 안 git clone)가 맞지 않았던 것이다.

## monorepo 케이스 (별도)

`gw-personal/Personal-Agent-Harness/`처럼 monorepo 안에 harness가 있는 경우는 **하네스 개발** 목적이며, 이번 “대상 프로젝트 적용” 문제와는 구분한다. `harness-dev` rule은 그 용도로 유지한다.
